# Architecture coverage and delivery gates

Review baseline: main at `9f1723b`, 2026-11-24. The [target architecture](TARGET-ARCHITECTURE.md) is suitable for incremental development. The three existing crates can accommodate these responsibilities as modules. No new process or public ABI is needed for the analysis path. This review maps every requirement family in specifications 00–27 to a boundary and a proof. A mapped family can still contain open decisions and unimplemented requirements. Individual IDs, priorities and acceptance criteria remain in the [canonical specifications](../requirements/README.md).

## Contracts for the first integrated analyzer

1. **Session and time.** The runtime owns start, timed sparse flush, subscription changes, stop/drain and generation invalidation. Every asynchronous result carries a generation. Reconnect creates a fresh generation even for the same adapter. Publication and subscription changes have a defined ordering. On stop, fence intake, flush accepted events, drain or report the recorder incomplete, then invalidate remaining work. Bound drain time. Queues may fill, so final health and known loss ranges must remain readable outside data queues.
2. **Memory across sessions.** A process-wide admission owner divides the user's managed RAM budget among sessions and component pools, including shared batches, recorder staging, indexes and query projections. Charge shared backing once until the last lease drops. Reserve recorder headroom at admission. On a budget decrease below current use, report current use and pending limit, deny new discretionary allocations and release or evict eligible pages. Never wait for an old UI lease on a capture worker. Fixture: two active sessions and a pinned page, lower budget, then release the pin. Observe aggregate usage and continued recorder progress. Report OS working set/RSS separately. The 350 MiB target applies to the standard profile.
3. **Recording and recovery.** Capture starts with a bounded RAM history. The optional cache worker extends Trace retention; the optional recorder streams into the selected destination only when manual start or a configured recording trigger activates it. Either worker can run alone. Trace reads use RAM first and page in older available data asynchronously. An optimization may reuse a finalized recording range only if its identity, coverage and availability match the requested history; recording filters or a stopped writer must never remove events from the independent Trace policy. See the [four storage-mode fixtures](../requirements/10-transmission-trigger-replay.md#live-capture-storage-modes-req-log-006). Temporary history eviction and disk quotas have no authority over durable user recordings. Track written, finalized and incomplete segments separately. Publish a completed segment only after the format writer finishes and all required I/O results are checked. After interruption, reopen prior finalized segments and identify the unfinished tail. Report recoverable ranges according to actual format capabilities. Verify with an independent reader, a full destination and termination during rollover.
4. **Offline and live identity.** A recording reader exposes bounded pages by recording, stream and stable position. Persist the mapping to source/channel, clock metadata and discontinuities within the format or a documented companion where necessary. Validate index identity against the recording before reuse. Rebuild a missing or stale index in cancellable bounded chunks. Link Trace, Inspector and Plot through explicit event/sample references and clock quality. Virtual replay uses a virtual destination. Physical transmission requires a separate authorized command.
5. **Competing workloads.** The host schedules offline indexing, spill and UI work independently of capture. Cap their pending bytes and outstanding I/O. On storage contention, throttle optional cache and indexing first. If recorder capacity is exceeded, retain an explicit incomplete outcome. Exercise a long recording with Trace spill enabled, repeated seeks and a slow display on the same volume.

## Decision and evidence order

| Gate | Owner and prerequisite | Exit record |
|---|---|---|
| Foundation | Core/runtime owns DEV-023/028. Desktop owns the independent DEV-024 proof. | Versioned session, loss and budget fixtures plus native GUI feasibility evidence. DEV-025 can build the shell independently of runtime delivery. |
| Virtual integration | Desktop and verification integrate DEV-008/009 after the runtime and shell contracts. | Demo through the normal service path, overload and stale-query results, timing and memory measurements on a declared host. |
| Physical and durable capture | HAL, project and storage owners deliver DEV-029/010/013/030. Before format selection compare actual reader round trips, metadata fidelity, interrupted files and licensing. | Named driver/OS matrix, independent-reader results, peak memory and at least 8 GiB written under a small profile. |
| Usable analyzer | Analysis and UX owners integrate DEV-011/031/032. | On Windows and Linux connect a verified adapter, filter Trace, inspect and plot a DBC signal, record, reopen and locate the same observation. Record any loss or unsupported metadata explicitly. |
| Later families | Protocol, automation and extension owners follow each canonical ADR and the v0.7 fixtures. | Before committing each delivery scope, enumerate its accepted IDs, open decisions, implementing modules, fixture, platform result and exclusions. Public compatibility claims require independent consumers. |

Use the numerical profiles and evidence rules in the [analysis baseline](../requirements/25-analysis-release-baseline.md). ADR-011's tighter latency hypotheses remain tuning goals unless separately accepted. Gate completion requires evidence on the applicable implementation commit. The first usable analyzer is a proposed delivery slice. Product-wide v1 scope, supported hardware and standard recording format remain decisions for their respective gates.
