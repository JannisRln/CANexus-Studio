## Benchmarks and measurement

The new UI targets below extend the [analysis reference profiles](../requirements/25-analysis-release-baseline.md#proposed-performance-and-memory-acceptance-gates). The 50,000 events/s workload remains the reference for comparing the two hosts. The 100,000 events/s figure is a stretch profile. Use the RAM and destination settings active in each run as inputs. Publish actual results separately from the targets.

| Scenario | Proposed workload and decision criterion |
|---|---|
| Hardware and build | One candidate reference box shared between Windows and Linux, a Ryzen 5 5600G-equivalent six-core system, 16 GiB RAM, SSD and fixed 1920×1080 60 Hz display. Reserve at least 128 GiB for the 24-hour recorder test or record an alternate retention policy. Record exact CPU, GPU/driver, OS version, compositor, renderer, Rust version, dependency lock, power mode and fixture hashes. Use release builds. Report Windows plus Linux/X11 and Linux/Wayland separately where the host offers both. |
| Startup and idle | Measure process launch to first input-capable presented frame across at least 20 cold starts. Proposed p95 < 1 s after the baseline gates. After 60 s quiet settle, measure CPU and main-process memory over 5 min. Compute CPU share as aggregate process CPU time divided by the product of elapsed wall time and the number of logical CPUs. Targets < 1% idle host CPU and < 100 MB idle main-process RSS/working set. Publish private bytes, GPU allocation and worker totals separately where available. Verify idle repaint counts. |
| Ingest and interactive Trace | Reuse the 50k events/s, 30-min reference, and test a second 100k events/s stress profile with the same CAN/CAN FD mix, seeded traffic and counts. Compare raw ingest and UI runs with a recorder/test sink. Expect zero GUI-induced acquisition loss and report driver, admission, decoder, recorder, history and view coalescing independently. Test 10M disk-indexed events with capped visible slices and cancellation. |
| Display and panel scale | Two live Trace views, ≥20 dockable panels registered and ≥100 live signals across numeric/plot views in the full engineering profile. Record visible vs hidden panels, update rates and panel counts. Target 60 FPS on the reference display during a sustained scroll/zoom, p95 UI render work ≤ 16.7 ms, and p95 input-to-present ≤ 50 ms over 200 timed inputs. Report presented frame intervals and misses independently of CPU render work. |
| Recording and soak | Run a representative 24-hour virtual session at a fixed 5k events/s plus a separate continuous ≥8 GiB recording with bounded RAM. Record file growth, independent-reader counts, buffer high-water marks and restart behavior. Include destination-full and writer-stall variants. Measure main-process memory and per-pool usage against the selected RAM profile. |
| Failure and recovery | Stall the view, hide a workspace, stop a consumer and drop a display during capture. Verify recording status remains responsive, captured identities agree with the headless run and render state recovers. Inject bad layouts, stale query generations and incompatible extension manifests. |

Compare the isolated GUI hosts using identical synthetic interaction scripts for shell, layout and idle measurements. Retain the Slint spike's actual measured scope when comparing old- and new-host results. Once DEV-008 lands, add the production Trace workflow as a new reference. Record three measured trials for sustained comparable scenarios, percentiles, raw artifacts, settings, observed variance and sampling units. Use ordinary CI for correctness and deterministic bounds. Use dedicated display/hardware hosts for performance, renderer behavior and timing claims. Verify Windows UI with a native screen reader and Linux with the target desktop stack's screen reader and checked AT-SPI plumbing.

## Implementation and integration rules

- Prepare separate feature branches, owned file sets and PRs using the repository's workflow. The dependency spike owns a standalone example and scratch feature pins. Cutover alone owns the production GUI manifests and shared CI. Keep Core-only and recording tasks parallelizable.
- Use the repository project-state validator plus Rustfmt, Clippy, build and tests for actual Rust changes. Run native and headless checks separately. Save fixture hashes and event counts, platform reports, screen-reader flows and performance run manifests and reference them by commit. See the requirements-to-evidence matrix in ADR-012.
- If an upstream/native gate fails, file the reproduction locally, identify the required fallback and adjust the feature matrix. A reversible in-window docking path keeps analysis usable while native float work continues. Preserve stable command IDs, persisted schema, project resources and existing tests through any fallback or toolkit adapter swap.
